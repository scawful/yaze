## 0. Summary

Oracle of Secrets renders two review pictures from a ROM with Python
(`Scripts/Maps/`): an underworld **room matrix** ($000-$127) and an
**overworld grid** (LW/DW/SW). scawful asked for this as a native yaze feature,
driven by project-file metadata, so any hacker can annotate and review their
own hack.

Atlas is:

1. A zelda3-level, ImGui-free **Atlas model** (`src/zelda3/atlas/`) built from
   the ROM facts yaze already reads (room census, doors, stairs, pits, chests,
   keys, entrances, overworld tiles) plus hand **annotations** from the project.
2. One **layout** step that turns the model into a display list, painted by
   two backends: ImDrawList (in-app) and a CPU rasterizer (PNG).
3. A CLI command `z3ed atlas-render`, MCP wrappers, and two cross-editor
   windows (Dungeon Atlas, Overworld Atlas) with hover, filter, click-through,
   live refresh and PNG export.

Six PRs, about 68 agent-hours and about 16 working days serialized. P1-P3 are
headless (zelda3 + CLI) and do not change editor behavior; P4-P5 add UI after
this week's editor freeze.

## 1. Goals and non-goals

### Goals

1. Reproduce both Oracle pictures in yaze with the same visual language
   (section 2.3), from any ALTTP-based ROM.
2. Generic by default: vanilla ALTTP gets built-in dungeon names, codes,
   colors and overworld sections. Nothing Oracle-specific is compiled in.
3. Project metadata: an `[atlas]` section in the `.yaze` file that points at
   one or more annotation files. The loader accepts Oracle's two existing
   files unchanged, so Oracle migrates by pointing at them.
4. One model for CLI, MCP and UI. The CLI JSON is the golden-test surface.
5. `z3ed atlas-render --project <.yaze> --view dungeon|overworld --out <png> [--json <path>]`,
   fast enough to run on every playtest build (target under 2 s for both
   views; the Python pipeline takes 49 s, see Appendix A).
6. In-app: click a cell to open the room/map, hover for details, filter by
   dungeon/region/status, refresh after edits, export PNG in the same look.

### Non-goals (v1)

1. Editing annotations inside yaze. v1 reads files and offers "Reload
   annotations" and "Reveal annotations file". In-app editing is open
   question Q6.
2. Runtime-accurate reachability (story flags, sprite blockers, overlays,
   Roc's Feather, Hookshot, walk-off edges without a door object). These stay
   out of the static model, as in the Oracle script. Annotations cover them.
3. Room or map thumbnails in cells. Cells are flat colors, as in Oracle's
   pictures. Section 5.7 names the invalidation key if thumbnails are added.
4. Pixel-identical PNGs to Oracle's output. Oracle uses macOS system fonts
   (Avenir Next, DIN Alternate); yaze ships its own fonts (section 5.4).
5. Replacing the Room Matrix panel in this cycle (open question Q1).
6. Any edit under `src/app/editor/overworld/*` (standing rule; see 5.7).

## 2. Reference implementation (Oracle `Scripts/Maps/`, read-only)

### 2.1 Data flow

| Script | Role |
|---|---|
| `map_rom.py` | ROM/SHA-1, `.sym` reader, z3ed runner with per-SHA-1 cache |
| `room_data.py` | Room matrix data: census + describe-room (296 calls) + list-pot-items (296 calls) + ROM tables |
| `ow_regions.py` | Overworld CSV: 4096 `overworld-find-tile` calls to rebuild tile grids, tile-type classification, edges, gate roles |
| `map_style.py` | Shared look: colors, `Canvas` (2x supersample, LANCZOS), pill, badge, dashed rect, card |
| `render_room_matrix.py` | Room matrix PNG + legend |
| `render_overworld_grid.py` | Overworld PNG + legend |
| `render_maps.py` | Runs both; writes `maps.json` |
| `room_annotations.json` | Dungeon codes, hand areas, room names, runtime pits, room-budget plans |
| `overworld_annotations.json` | Regions, map names, gate notes, special-camera maps, non-pad links |

Room facts that the Python adds on top of `z3ed dungeon-room-census`:

1. Status `orphan` (census: `in_use` + `orphan` flag) and `reserved`
   (free room that a dream warp lands in).
2. Door categories and gutter pairing (`DOOR_CAT`, `pair_doors`): outer wall
   when tile <= 8 or >= 50, position = tile + 2, pair with the facing wall of
   the grid neighbour within 3 tiles, strongest category wins
   (`bigkey > key > shutter > bomb > open > onesided`), unmatched = hollow
   (one side only), a normal door within 2 tiles of an exit marker is the exit.
3. Pills parsed from census reference `detail` strings ("pits in", "warp
   tiles in", "RoomsWithPitDamage", "tag-driven").
4. Chests (IDs `0x24` K, `0x25` C, `0x32` BK, `0x33` M), pot keys (pot item
   `0x08`), enemy key drops (sprite list id `0xE4`, byte0 `0xFE`/`0xFD`).
5. Dream warps from symbol `Oracle_Link_WarpToRoom_room` in the ROM's `.sym`.
6. Interior names parsed from `Overworld/entrances.asm` comments.

Overworld facts (all computed in Python from the swept tile grids):

1. Tile types: tile16 words at PC `0x1E8000` (expanded flag PC `0x02FD28` !=
   `0x0F`) else `0x78000`; type = `OverworldTileTypes[word & 0x1FF]`, PC
   `0x71459`.
2. 8x8 cell classes: free, water (`0x08`, `0x0B`), ledge (`0x28`-`0x2F`),
   Glove (`0x52`, `0x55`), Mitt (`0x53`, `0x56`), Boots (`0x57`), Hammer
   (tile16 `0x21B`), pit (`0x20`), solid (everything else).
3. Edge status between maps with different parents: open if >= 2 facing cell
   pairs are both free, swim if >= 2 are both water, gate if any gate cell,
   else blocked. Maps in `special_edge_block` are always blocked (special
   camera).
4. Gate role by flood fill: ROUTE if the gate component touches >= 2 free
   components of >= 300 cells; POCKET if it touches a small (8-299) one;
   DECOR otherwise. Only ROUTE (white ring) and POCKET (grey ring) get badges.
5. Warp pads: any tile16 quadrant of type `0x4B`; a pad on map M lands on
   M ^ `0x40` (vanilla mirror-warp rule).

### 2.2 How the data is used

`Docs/Planning/Reviews/audit_2026-09-26/overworld_regions.md` builds region
tables, walking edges and gate routes from `overworld_regions.csv`.
`warp_scan.md` verifies warp tiles (`0x4B`, handler `$07:DEFF`), the
destination rule and the accidental char-alias warp spots on `$31`. Both
audits name tool traps that Atlas should remove: `overworld-find-tile --tile`
parses hex, `overworld-get-tile` indexes the whole world array, and
`overworld-export-graph` reads vanilla transition tables.

### 2.3 Visual language (measured from `room_matrix.png`, `overworld_grid.png` and the source)

All sizes are logical pixels. Oracle draws at 2x and scales down with
LANCZOS: room matrix x1.5 (4395x3606 px), overworld x1.6 (4404x3657 px).

Shared palette (`map_style.py`):

| Token | RGB | Use |
|---|---|---|
| `bg` | 15,17,22 | page background |
| `card` | 24,27,34 | legend cards, radius 12 |
| `pill_bg` | 18,18,24 | pill fill |
| `white` / `text` / `muted` / `dim` | 245,245,248 / 215,220,230 / 165,170,185 / 110,114,126 | text tiers |
| `empty` | 30,33,40 | unowned/free cell fill |
| `pad` | 172,110,255 | warp pad / warp tile links |
| `special` | 255,205,70 | entrances, holes, special links |
| `warn` | 255,110,110 | cross-area ring, test links |
| `edge.open` / `swim` / `special` / `blocked` | 70,220,110 / 80,160,255 / 140,144,156 / 230,70,70 | overworld edges |

Text on a cell uses dark text (18,20,26) when fill luminance > 150, else
light (240,242,246).

**Room matrix** (`render_room_matrix.py`):

- Grid: 16 columns, cell 130x100, gutter 16, radius 8. Column labels `+0`..`+F`,
  row labels `00`..`F0` in `dim`. Rows $100-$127 sit 44 px lower under the
  header "UPPER ROOMS $100–$127" and a note on 9-bit room IDs. Legend column
  440 wide on the right.
- Cell: fill = owner area color; room ID top-left (DIN 19); name in two
  wrapped lines (demi 11). Free, reclaimable and reserved cells use `empty`
  (reclaimable: 44,42,38) and print the status word in bold status color.
- Status outline 2.6 px: FREE 70,220,110; RECLAIMABLE 255,205,70; ORPHAN
  255,140,60; RESERVED 255,150,210.
- Plans: dashed inner rectangle, inset 4.5, width 1.8, dash 7 / gap 5, plus a
  bold label line. Colors come from the plan (Oracle: TOWER 90,220,255;
  SHRINE 120,170,255; TEMPLE 205,175,255; RESERVE 170,174,186).
- Door markers in the gutters, placed at `pos/64` along the wall: rounded
  rect 8x18 (east/west gutters) or 18x8 (north/south), radius 3. Colors:
  open 70,220,110; shutter 110,165,255; key 255,214,64; big key 255,92,92;
  bomb/dash 200,152,110; other 160,160,170. Hollow (door on one side only):
  `bg` fill, 1.8 outline, shifted 2 px toward the room that has the door.
  Exit to the overworld: white bar 16x3.5 (250,250,252) inside the wall.
- Pills: height 16.5, padding 5, full radius, condensed demi 10.5, `pill_bg`
  fill, colored text. They stack bottom-up, at most two rows, overflow as
  `+N`. Text and color: `ENT 0C · OW 50` and `HOLE 7B · OW 57` gold;
  `SPAWN 1` 120,220,210; `DREAM 2 IN` 255,150,210; `STAIR 11D` 150,192,255;
  `PIT 05` 255,146,90; `WARP 0D` / `WARP·Q ...` purple; `PIT DMG`
  226,120,140; `TAG PIT 19` dim. A 1.6 px `warn` ring marks a link that lands
  in another area.
- Badges, top-right, right-aligned, 3 px apart, 17 px: BK (232,80,80, white
  ring), BC (square, 214,160,58), C (92,204,192), M (156,222,120), K
  (255,214,64; `K2` for two), grey count (150,154,166) for other chests.
  Hollow ring variant (fill 20,20,26, ring = badge color) = key from a pot or
  an enemy drop.
- Legend cards: Areas (swatch, code, name, count), Room status (+ plans),
  Doors, Links, Chests and keys (per-area table: K chest, K pot, K drop, BK,
  BC, C, M), Data sources.

**Overworld grid** (`render_overworld_grid.py`):

- Cell 150x108, gutter 12, radius 8. LW 8x8 top-left; DW 8x8 below (row
  offset 9.35); SW split in two 4x4 blocks on the right (columns 0-3 at
  (8.25, 1), columns 4-7 at (9.25, 6.1)). Section headers bold 24 + subtitle.
- Large areas are one merged block with a 2.5 px white outline and quadrant
  lines in `darker(fill, 28)`, 1.5 px.
- Region colors: golden-ratio hues per world (LW sat 0.32 val 0.90 offset
  0.02; DW 0.42 / 0.60 / 0.10; SW 0.30 / 0.78 / 0.47); `SW unused/blank`
  58,60,68.
- Map ID DIN 22 top-left, name demi 12.5 (one line when two pills).
- Gate badges, r = 10, top-right: G (196,200,208), M (10,10,12, white text),
  H (232,138,52, square), B (88,176,255). White ring = ROUTE, grey ring
  (110,110,120) = POCKET only.
- Edge markers: open/swim/special = 16x10 pill in the gutter center; blocked =
  3 px red line along the cell side, inset 10.
- Pills: height 18, radius 9, bold 11. `PAD to 42` / `PAD from 02` purple,
  `TO 80` gold, `TEST BRIDGE TO 84` red.

## 4. Gaps (what does not exist yet)

1. **`[atlas]` in the project file.** `YazeProject::ParseFromString`
   ignores unknown sections and the serializer writes only known ones, so a
   hand-written `[atlas]` section is lost the next time yaze saves the
   project. P1 must add parse + serialize + a round-trip test before anyone
   documents the key.
2. **`--project <.yaze>` resolution in the census CLI.**
   `dungeon_census_commands.cc` `ResolveCodeFolder` uses `code_folder` only.
   Oracle's `.yaze` has `code_folder=Core`, so the registry under
   `Docs/Dev/Planning/` is not found and the command silently falls back to
   derived owners, exit 0. Measured on a copy (2026-09-27): `--project <repo>`
   gives free 14 / reclaimable 6 / in use 276 / orphan 2; `--project
   Oracle-of-Secrets.yaze` gives 14 / 4 / 278 / 1 with
   `owners_source=derived_from_entrances`. `atlas-render` must open the
   project with `YazeProject::Open` (which has manifest-dir and project-dir
   fallbacks) and fail loudly when `--project` is given but no registry or
   annotations load.
3. **One entrance-table reader.** The census reads bank $0F; `RoomEntrance`
   and `overworld-export-graph` read the vanilla table. Extract the census
   reader into zelda3 and use it everywhere Atlas reads entrances.
4. **Door category per room edge.** Census door facts have direction, along,
   outer, but no type. Door categorization and gutter pairing (section 2.1)
   exist only in Python.
5. **Overworld walkability.** No reader for `OverworldTileTypes`, no cell
   classifier, edge classification, flood fill or gate roles.
6. **Gate detection from sprites.** Not modeled anywhere (also not in the
   Python). v1: annotations only.
7. **Transport/whirlpool and special-area triggers.** Constants exist
   (`overworld_exit.h`), no reader. v1: annotation links.
8. **Text in headless rendering.** Only a 3x5 hex-digit bitmap font exists.
9. **Change signals.** `RomModifiedEvent` is never published; `zelda3::Overworld`
   has no revision; `Room::composite_source_revision()` is documented for
   object, layout and palette changes and is not verified for sprites,
   chests or header bytes.
10. **Correct vanilla overworld names.** The existing table is wrong (section 3).
11. **Name collision.** `gfx::AtlasRenderer` and `gfx::TextureAtlas`
    (`src/app/gfx/render/`) already use "atlas" for texture atlases. Atlas
    code uses namespace `yaze::zelda3::atlas` / `yaze::gfx::world_atlas` and
    type names `DungeonAtlas`, `OverworldAtlas`, never a bare `Atlas*`.

### 5.2 Atlas model (zelda3, no ImGui)

```cpp
namespace yaze::zelda3::atlas {

enum class RoomStatus : uint8_t { kInUse, kFree, kReclaimable, kOrphan, kReserved };
enum class DoorCategory : uint8_t { kOpen, kOneSided, kShutter, kKey, kBigKey,
                                    kBomb, kExit, kKeyStairs, kOther };
enum class LinkKind : uint8_t { kEntrance, kHole, kSpawn, kStair, kPit,
                                kWarpTiles, kWarpTag, kPitDamage, kTagPit,
                                kRuntime /* annotation or symbol link */ };
enum class Provenance : uint8_t { kRom, kRegistry, kAnnotation, kSymbol, kDefault };

struct AtlasLink { LinkKind kind; int from = -1; int to = -1; int entrance = -1;
                   int ow_map = -1; bool cross_area = false; std::string label;
                   Provenance source; std::string source_ref; };

struct DungeonAtlasRoom {
  int room_id; std::string area;            // area key ("D1", "HOS", "INT", "NONE")
  int owner_index; RoomStatus status; bool reached, empty, interior;
  std::string name; std::vector<std::string> reasons, plans;
  std::vector<AtlasLink> links_out;         // pills, drawn in the source room
  std::vector<AtlasLink> links_in;          // entrances, holes, spawns, runtime
  struct Badges { int k_chest, c, m, bk_chest, big_chest, other,
                  k_pot, k_drop, bk_drop; } badges;
  bool pit_damage; std::vector<ExitMark> exits;
};
struct DoorEdge { int a, b; char dir; int pos; DoorCategory category;
                  bool both_sides; bool one_sided_type; };
struct DungeonAtlas { std::vector<DungeonAtlasRoom> rooms;   // 0x128
                      std::vector<DoorEdge> edges; std::vector<AreaInfo> areas;
                      std::vector<PlanInfo> plans; KeyTable key_table;
                      RomIdentity rom; std::vector<std::string> warnings; };

struct OverworldCellClass { /* 8x8 cells per world: free, water, ledge,
                              glove, mitt, boots, hammer, pit, solid */ };
struct OverworldAtlasMap { int map_id, parent; AreaSize size; std::string world,
                           region, name; std::vector<GateInfo> gates;
                           std::vector<AtlasLink> links; int deep_water,
                           warp_tiles; };
struct MapEdge { int a, b; char dir; EdgeStatus status;  // open, swim, gate,
                 int walk_cells, swim_cells; Provenance source; };  // blocked, special
struct OverworldAtlas { std::vector<OverworldAtlasMap> maps;       // 0xA0
                        std::vector<MapEdge> edges; std::vector<SectionInfo> sections;
                        std::vector<RegionInfo> regions; RomIdentity rom;
                        std::vector<std::string> warnings; };

// Inputs are plain data so tests can build them without a ROM.
absl::StatusOr<DungeonAtlasInput> CollectDungeonAtlasInput(Rom*, const CollectOptions&);
DungeonAtlas BuildDungeonAtlas(const DungeonAtlasInput&, const AtlasAnnotations&);
absl::StatusOr<OverworldAtlasInput> CollectOverworldAtlasInput(const Overworld&, Rom*,
                                                               const CollectOptions&);
OverworldAtlas BuildOverworldAtlas(const OverworldAtlasInput&, const AtlasAnnotations&);
}
```

Rules:

1. `CollectDungeonAtlasInput` calls `CollectRoomCensusInput` once and adds
   per-room extras (door types, chest item IDs, pot keys, key drops). No
   second pass over 296 rooms. The census stays the single source of
   status, owners and reachability.
2. `CollectOptions` carries an optional `RoomSource` (`std::function<const
   Room*(int)>`) so the UI can supply live, unsaved rooms; missing rooms load
   from the ROM.
3. `BuildDungeonAtlas` derives: `orphan` (census flag), `reserved` (free or
   reclaimable room that a runtime or symbol link lands in, or listed with
   status `reserved`), area (registry owner → dungeon code; else annotation
   area; else `INT`/`OTHER`/`NONE`), links and cross-area flags, door edges,
   badges and the per-area key table.
4. `BuildOverworldAtlas` classifies cells from `Overworld::GetMapTiles(world)`
   and `tiles16()` in memory. The 4096-subprocess sweep disappears.
5. Every derived field records its provenance, so the JSON and tooltips can
   say "ROM", "registry", "annotation: <file>", "symbol: <label>" or "default".

### 5.3 Annotation loader and merge order

Sources, lowest to highest precedence:

1. Built-in vanilla defaults (`atlas_defaults.cc`), unless `defaults = none`.
2. Project registry (`hack_manifest` `ProjectRegistry`): dungeon IDs and
   names, overworld area names and world names.
3. Resource labels (`room`, `entrance`, `overworld_map`).
4. Annotation files from `[atlas] annotations`, in listed order.

Scalars: last writer wins. Lists keyed by an ID (`areas.key`, `plans.key`,
`links.id`) merge by ID; lists without IDs concatenate. The loader returns
warnings (unknown keys, rooms outside $000-$127, maps outside $00-$9F,
annotation that duplicates a ROM fact, v0 lists that disagree) and errors
(bad JSON, bad hex, unknown schema). Errors fail the CLI with exit 2; the UI
shows them in the window's status line and keeps the last good model.

File type is detected from content: `"schema": "yaze.atlas/1"` → v1;
top-level `dungeon_codes` / `areas` / `plans` → Oracle room v0;
`regions` / `gate_notes` / `links` → Oracle overworld v0.

### 5.4 Renderer: one layout, two painters

1. `atlas_layout` turns a model plus a filter into a `Scene` in logical
   pixels: primitives, text runs (string, role, size, color) and hit regions
   (`{rect, kind: room|map|pill|door|legend_row, id, target}`). Layout is
   deterministic and knows nothing about ImGui or pixels.
2. Text measurement uses `atlas_text` (stb_truetype on the embedded TTF), in
   both painters, so wrapping and pill widths are identical in the app and
   the PNG.
3. ImDrawList painter: draws the scene at canvas zoom; text via an `ImFont`
   loaded from the same TTF bytes (`AddFontFromMemoryTTF`, not owned by the
   atlas), drawn at scene size x zoom (ImGui 1.92 dynamic sizes).
4. CPU painter: rasterizes at 2x with coverage anti-aliasing (rounded rect,
   ellipse, thick line, dash), stb_truetype glyphs, box downscale to the
   output scale, then `util::EncodeRgbaPng` (miniz; no libpng, works in WASM).
5. In-app "Export PNG" calls the CPU painter, not a screenshot. The export is
   byte-identical to `z3ed atlas-render` for the same ROM, project and filter.
6. Fonts: embed `Roboto-Medium.ttf` (163 KB) for all text roles; bold roles
   use a 0.5 px double-strike in both painters. Oracle's condensed pill face
   and DIN IDs have no shipped equivalent; layout widths grow accordingly
   (pill rows wrap earlier). This is the main visible difference from
   Oracle's PNGs.

### 5.5 CLI: `atlas-render`

```
z3ed atlas-render --project <.yaze> --view dungeon|overworld --out <png>
                  [--rom <sfc>] [--json <path>] [--csv <path>]
                  [--annotations <file>[,<file>...]] [--defaults vanilla|none]
                  [--symbols <sym>] [--scale <0.5-3>] [--filter <expr>]
                  [--no-legend] [--format json|text]
```

1. `--project` opens the project with `YazeProject::Open`; ROM = `--rom`, else
   `[files] rom_filename`. Oracle passes `--rom` (playtest ROM).
2. `--json` writes the model (schema `yaze.atlas.dungeon/1` or
   `yaze.atlas.overworld/1`; Appendix B). `--csv` writes the Oracle-compatible
   CSV columns (`room_matrix.csv`, `overworld_regions.csv`) so audit scripts
   keep working.
3. stdout: a JSON summary (paths, ROM SHA-1, counts, warnings), like
   `overworld-render`.
4. `--out` alone (no `--project`) works on any ROM with vanilla defaults.
5. Read-only: never writes the ROM; output paths go through
   `ExecuteWithContext` like `overworld-render`, so they cannot alias the ROM.
6. Symbol lookup order: `--symbols`, `<rom>.sym` next to the ROM (matches the
   Python), `[atlas] symbols`, `[files] symbols_filename`.

### 5.6 In-app Atlas workspace

1. Two windows: `atlas.dungeon` "Dungeon Atlas" (category Dungeon) and
   `atlas.overworld` "Overworld Atlas" (category Overworld), workflow group
   "Atlas", `WindowLifecycle::CrossEditor` with a default pin, so a
   click-through that switches editors does not hide the Atlas. A layout
   preset "Atlas" opens both side by side.
2. Toolbar: search (room/map ID or name), filter chips from the legend
   (dungeon/area, region, status: FREE, RECLAIMABLE, ORPHAN, RESERVED,
   PLANNED; link kinds), overworld phase selector (0/1/2/all), zoom (fit,
   100%), Export PNG..., Export JSON..., Reload annotations, status line
   (ROM SHA-1, annotation files, warnings count).
3. Canvas: `gui::Canvas` pan and zoom. Non-matching cells dim to 25% alpha
   instead of disappearing, so the grid stays spatial.
4. Every cell is an ImGui item with a stable ID (`##atlas_room_%03X`,
   `##atlas_map_%02X`, `##atlas_pill_<room>_<n>`) via `ItemAdd` +
   `ButtonBehavior`, so ImGuiTestEngine can target it.
5. Hover: tooltip with ID, name, owner/region, status + census reasons,
   doors, links in/out, chests and keys, gates and edge counts, plans, and
   provenance per line.
6. Click a cell: publish `JumpToRoomRequestEvent` / `JumpToMapRequestEvent`.
   Click a pill: jump to the link target (for example `STAIR 11D` opens room
   $11D, `ENT 0C · OW 50` opens map $50).
7. Right-click (`gui::ItemContextMenu`, order per
   `docs/internal/gui/context-menus.md`): Open Room / Open Map, Jump to
   linked..., Render Area (overworld, via `RenderOverworldArea`); Copy Room
   ID, Copy as JSON; Filter to this Dungeon/Region, Reveal Annotations File.
   No destructive items.
8. Legend: collapsible side card with the same rows as the PNG legend; a
   click on a legend row toggles that filter.

### 5.7 Live refresh

No new editor hooks are required; every source is polled cheaply while an
Atlas window is visible (4 Hz), and push events are a later optimization.

| Change | Detection | Rebuild |
|---|---|---|
| Dungeon edit (loaded room) | Per-room fingerprint over the fields Atlas reads (doors, header stair/holewarp bytes, tags, object count, sprites + key drops, chests, pot items); `composite_source_revision()` as a fast pre-check | That room's facts, then `BuildRoomCensus` + `BuildDungeonAtlas` (pure; the census takes about 0.1 s for all 296 rooms from a ROM, less from facts) |
| Overworld edit | Per-map fingerprint over the 32x32 tile16 IDs, entrances/holes/exits on the map, sprites per phase, parent/size; one hash over `tiles16()` quadrant IDs | Changed maps + grid neighbours; a `tiles16()` change reclassifies all maps |
| ROM load/unload, session switch | `RomLoadedEvent`, `RomUnloadedEvent`, `SessionSwitchedEvent` | Full rebuild on a ROM copy in the background (census overlay pattern) |
| Save | Covered by the room/map fingerprints | - |
| Annotation file edit | mtime poll, 1 Hz | Re-merge annotations, rebuild both models |
| Graphics sheets | Not an input in v1. If thumbnails are added: key by `Room::composite_source_revision()` (already folds `GraphicsSheetStore::Revision` via `SourceSheetsChanged`) | - |

Live overworld state comes from `CurrentOverworldEditor()->overworld()`
(`overworld_panel_access.h`, include only). If the Overworld editor has not
loaded, the session loads a private `zelda3::Overworld` from a ROM copy in the
background. A push event (`AtlasContentChangedEvent{kind, id}` published by
the editors, or finally publishing `RomModifiedEvent`) needs a small edit in
`src/app/editor/overworld/*` and is gated on scawful's green light (Q5).

### 5.8 MCP

1. New `~/src/tools/yaze-mcp/core/z3ed_atlas.py` with `register(mcp)`,
   reusing `run_z3ed`, `resolve_rom`, `find_project_file` from
   `z3ed_overworld.py`.
2. Tools: `atlas_render(view, out_path="", project="", rom_path="",
   annotations="", filter="", include_image=True)` returns the JSON summary
   and the PNG; `atlas_cell(view, id, project="", rom_path="")` returns one
   room or map row with links and provenance (runs `atlas-render --json` to a
   cached temp file keyed by ROM SHA-1 + annotation mtimes).
3. `REQUIRED_CAPABILITIES` gains `"atlas_render": ("atlas-render", "--view")`
   so `z3ed_status` reports a stale binary.
4. `~/src/tools/yaze-editor/server.py` loads `core/z3ed_atlas.py` by path,
   the same way it loads `z3ed_overworld.py`.
5. Read-only; no write refusal logic needed.

## 6. Annotation schema v1

### 6.1 Where it lives

The `.yaze` file holds pointers and scalars only; structured data lives in
JSON sidecars. Reason: the `.yaze` format is flat `key=value` INI
(`ParseKeyValue`), and nested lists (rooms per plan, maps per region) do not
fit it.

```ini
[atlas]
# Annotation files, merged in order (v1 or Oracle v0), relative to the project file.
annotations=Docs/Atlas/atlas.json
# vanilla (default) or none
defaults=vanilla
# Optional .sym for symbol_links; default: <rom>.sym, then [files] symbols_filename
symbols=
# Default folder for the in-app Export buttons
export_folder=Roms/Maps
```

| Key | Type | Default | Meaning |
|---|---|---|---|
| `annotations` | comma list of paths | empty | Annotation files, merged in order |
| `defaults` | `vanilla` \| `none` | `vanilla` | Include the built-in vanilla set |
| `symbols` | path | empty | Symbol file for `symbol_links` |
| `export_folder` | path | project dir | In-app export target |

P1 adds `AtlasSettings` to `YazeProject`, parse and serialize, and a
round-trip test. Bundles (`.yazeproj`) keep sidecars inside the bundle;
bundle export must copy the listed files (P6 check).

### 6.2 Field table (v1)

### 6.3 JSON Schema (v1, abridged)

```json

  "$id": "https://github.com/scawful/yaze/schemas/atlas-annotations-1.json",
  "type": "object",
  "required": ["schema"],
  "properties": {
    "schema": {"const": "yaze.atlas/1"},
    "title": {"type": "string"},
    "about": {"type": "string"},
    "dungeons": {"type": "array", "items": {"type": "object",
      "properties": {"owner": {"type": "string"}, "dungeon_id": {"$ref": "#/$defs/id"},
                     "code": {"type": "string", "maxLength": 4},
                     "name": {"type": "string"}, "color": {"$ref": "#/$defs/color"}},
      "anyOf": [{"required": ["owner"]}, {"required": ["dungeon_id"]}]}},
    "areas": {"type": "array", "items": {"type": "object", "required": ["key", "rooms"],
      "properties": {"key": {"type": "string"}, "code": {"type": "string", "maxLength": 4},

                     "rooms": {"$ref": "#/$defs/idList"}, "source": {"type": "string"}}}},
    "rooms": {"type": "object", "propertyNames": {"$ref": "#/$defs/idString"},
      "additionalProperties": {"type": "object", "properties": {
        "name": {"type": "string"}, "status": {"enum": ["reserved"]}, "note": {"type": "string"}}}},
    "links": {"type": "array", "items": {"type": "object", "required": ["view", "kind", "from"],
      "properties": {"id": {"type": "string"}, "view": {"enum": ["dungeon", "overworld"]},
        "kind": {"enum": ["pit", "warp", "stair", "pad", "whirlpool", "special", "dream", "warn"]},
        "from": {"$ref": "#/$defs/id"}, "to": {"$ref": "#/$defs/id"},
        "label": {"type": "string"}, "source": {"type": "string"}}}},
```

### 6.5 Migration from Oracle's files (field by field)

Oracle keeps its two files and adds `[atlas] annotations=Scripts/Maps/room_annotations.json,Scripts/Maps/overworld_annotations.json`.
The v0 adapter maps them as follows.

`room_annotations.json`:

| Oracle v0 field | v1 field | Notes |
|---|---|---|
| `_about` | `about` | Ignored |
| `dungeon_codes` `{registry_id: code}` | `dungeons[] {owner: registry_id, code}` | Names come from the registry (`dungeons.json`) |
| `areas[].key` / `name` / `rooms` / `source` | `areas[]` same fields | - |
| (hard-coded `AREA_COLOR`, `CODE` in `render_room_matrix.py`) | `areas[].color`, `areas[].code`, `dungeons[].color` | Oracle adds these optional keys to its v0 file (the Python ignores unknown keys). Without them yaze assigns palette colors and uses the key as the code |
| `room_names {room: name}` | `rooms.<room>.name` | - |
| `runtime_pits[] {room, to, source}` | `links[] {view: dungeon, kind: pit, from: room, to, source}` | Lint warning once the census reports the same pit |
| `plans[].key` / `label` / `name` / `status` / `rooms` / `source` | `plans[]` same fields | - |
| (hard-coded `PLAN_COLOR`) | `plans[].color` | Same treatment as area colors |
| (symbol `Oracle_Link_WarpToRoom_room` in `room_data.py`) | `symbol_links[] {symbol, count: 3, width: 1, kind: dream, label: "DREAM {n} IN"}` | Oracle adds this entry |
| (`Overworld/entrances.asm` comment parsing) | resource labels `entrance` / `room`, or `rooms.<id>.name` | Oracle moves interior names into labels; until then the `name` field of INT rooms differs (known diff) |
| (hard-coded title "Oracle of Secrets — ...") | `title` or `[project] name` | - |

`overworld_annotations.json`:

| Oracle v0 field | v1 field | Notes |
|---|---|---|
| `_about` | `about` | Ignored |
| `regions {"LW Name": [maps]}` | `overworld.regions[] {name: "Name", world: "LW", maps}` | The `LW `/`DW `/`SW ` prefix becomes `world` |
| `names {map: name}` | `overworld.maps.<map>.name` | - |
| `gate_notes {"map:Gate": note}` | `overworld.gates."map:Gate".note` | Roles stay automatic; notes starting with `ACCIDENTAL` do not set `suppress` automatically (Oracle decides) |
| `special_edge_block [maps]` | `overworld.closed_border_maps` | - |
| `sw_isolated_maps [maps]` | `overworld.isolated_maps` | - |
| `links[] {map, text, kind}` | `links[] {view: overworld, from: map, label: text, kind}` | Label-only pills keep Oracle's exact text; converting pairs (`TO 81` / `FROM 0F GRAVEYARD`) to one `from`/`to` link is optional |
| (hard-coded section titles and SW split in `pos()`) | `overworld.sections[]` | Oracle adds 4 entries (KALYXO, SPECIAL WORLD, SKY ISLANDS + UNUSED, EON ABYSS / YESTERWIND) |
| (hard-coded legend notes) | `legend_notes.overworld[]` | - |

What stays built into yaze (style, not project data): door, link, badge,
status and edge colors; pill, badge and cell geometry; the vanilla tile-type
sets, item IDs and door categories (overridable where section 6.2 says so).

## 7. Oracle output vs yaze census: known disagreements

Measured on 2026-09-27 from Oracle's b28 output (`Roms/Maps/`, ROM SHA-1
`3b522b4b...`) and a scratch run on `oos168.sfc` (Appendix A).

| # | Topic | Oracle Python | yaze census / Atlas | Handling |
|---|---|---|---|---|
| 1 | Status | Adds `orphan` and `reserved` statuses | Census: `in_use` + orphan flag; no reserved | Atlas derives both the same way; no diff expected |
| 2 | D3 $81 pit ring → $05 | `runtime_pits` annotation | Census misses it (static) | Annotation link; #261 follow-up ("runtime/tag/tile holes") may detect it, then the loader warns about a duplicate |

| 11 | Tile grids | 4096 `overworld-find-tile` calls | In-memory `map_tiles` | Must match exactly (0 gaps in both) |
| 12 | Tile16 base / parents | Flag at PC `0x02FD28`; parents PC `0x140998`, sizes PC `0x1788D` | Overworld loader version detection; `OverworldMap::parent()` | Must match; the audit found parents equal to `describe-map` for all 160 maps |

Golden handling:

1. The comparator normalizes both sides (hex case, list order, room ID
   format `0x%02X`/`0x%03X`) and drops presentation-only fields (timestamps,
   paths, z3ed version, `area_source` wording).
2. Known differences live in `test/fixtures/atlas/oracle_b28_known_diffs.json`:
   `{view, id, field, oracle, yaze, class, reason, until}` with `class` in
   `yaze-fix-pending`, `oracle-heuristic`, `annotation-only`.
3. The test fails on any diff not in the allowlist and on any allowlist entry
   that no longer reproduces. A fix (for example the #261 hole work) must
   delete its allowlist entries in the same PR.
4. PNG goldens are yaze-only (Oracle's fonts are not available); parity with
   Oracle is checked at the JSON level only.

## 10. Risks

1. **Oracle leakage.** Oracle names or colors compiled into yaze. Mitigation:
   all project data through annotations; a unit check that
   `src/zelda3/atlas/` and `src/app/gfx/world_atlas/` contain none of the
   strings in Oracle's annotation files.
2. **Project file loss.** Hand-written `[atlas]` dropped on save (gap 1).
   Mitigation: P1 lands parse + serialize before the guide documents the key.
3. **Silent wrong owners.** `--project <.yaze>` resolution (gap 2).
   Mitigation: `YazeProject::Open` + loud failure; separate census CLI fix.
4. **Heuristics.** Door pairing, edge walkability and gate roles are Oracle's
   heuristics, not game rules. Known limits: walk-off edges, sprite gates,
   overlays, story flags, Feather/Hookshot. Mitigation: port verbatim, parity
   goldens, annotation overrides, tooltips show "inferred".
5. **Visual parity.** No Avenir/DIN; wider pills wrap earlier. Mitigation:
   yaze-only PNG goldens; ask scawful to accept the font change (Q7).
6. **Live refresh without hooks.** Polling cost and missed fields.
   Mitigation: fingerprints over exactly the fields the model reads; a test
   per edit kind; push events after the overworld green light (Q5).
7. **UI overlap.** Room Matrix, the Workbench "Connected" canvas mode and the
   Dungeon Atlas all show room layouts. Mitigation: Q1; at minimum the census
   overlay reads owner colors from the Atlas defaults (one palette).
8. **Wrong vanilla overworld names** leaking in through `Zelda3Labels`
   (gap 10). Mitigation: verified table in P2; the old table gets a
   follow-up task.
9. **Name collision** with `gfx::AtlasRenderer` / `TextureAtlas` (gap 11).
10. **CI coverage.** ROM parity runs only locally/nightly. Mitigation:
    fixture-model E2E and render goldens in CI; pinned SHA-1s.
11. **Shared-code churn.** P1 touches `room_census.cc` while #261 follow-ups
    are open. Mitigation: start P1 after they merge; keep census changes to
    added fields.
